Bluetooth Provisioning Flow
First-time setup only · WiFi flow removed
ⓘ WiFi credentials (SSID/Password) and the User Secret are transmitted over Bluetooth (BLE) during initial setup. No HTTP auth API is used for provisioning. Once the controller joins WiFi, the User Secret becomes the permanent authentication key for all API calls.

Discovery
Two ping endpoints · One unauthenticated, one authenticated
ⓘ All endpoints after auth require header: Authorization: Bearer <user-secret>. The secret entered during provisioning (separate from WiFi password) serves as the permanent authentication key.
GET /api/ping Unauthenticated ping — is controller alive? ▶
Called immediately after mDNS discovery. No auth header. Returns only basic identity — no sensitive WiFi or config data.
Request
GET /api/ping // No Authorization header needed
Responses
// 200 OK { "ok": true, "deviceId": "DMX-CTRL-A4F2", "firmwareVersion": "2.1.0", "rdmSupported": true, "uptimeSeconds": 3600 } // 503 Busy { "ok": false, "error": "controller_busy" }
GET /api/ping/details Authenticated ping — full status including WiFi details ▶
Requires the User Secret in the Authorization header. Returns full controller status including current WiFi network details. Use this as a heartbeat to verify connection is still alive.
Request
GET /api/ping/details Authorization: Bearer <user-secret>
Responses
// 200 OK { "ok": true, "deviceId": "DMX-CTRL-A4F2", "controllerName": "Stage Left", "firmwareVersion": "2.1.0", "rdmSupported": true, "uptimeSeconds": 7200, "wifi": { "ssid": "VenueWiFi_5G", "ip": "192.168.1.42", "signal": -58, "connected": true } } // 401 Secret invalid / incorrect { "error": "unauthorized" }

RDM — Remote Device Management
Requires hardware bidirectional DMX · Mfr ID: 06AEh
⚠ Only available when rdmSupported: true in GET /api/ping. All Canara fixtures use Manufacturer ID 06AEh · Manufacturer: Canara Lightings.
GET /api/rdm/discover Scan DMX line for RDM-capable fixtures ▶
Request
GET /api/rdm/discover Authorization: Bearer <user-secret>
Responses
// 200 OK { "discovered": [ { "uid": "06AE:00000001", "manufacturerId": "06AEh", "manufacturerName": "Canara Lightings", "dmxAddress": 1, "label": "Spot 1" } ], "scannedAt": "2026-05-10T10:30:00Z" } // 503 Not supported { "error": "rdm_not_supported" }
GET /api/rdm/devices/{uid} Get full info for one RDM fixture ▶
// 200 OK { "uid": "06AE:00000001", "manufacturerId": "06AEh", "manufacturerName": "Canara Lightings", "modelId": "m26", "modelName": "Color Fresnel", "dmxAddress": 1, "dmxFootprint": 8, "firmwareVersion": "1.4.2", "label": "Spot 1" } // 404 { "error": "rdm_device_not_found" }

{ "identify": true } // false to stop identify mode
Response

Network & System
Update WiFi · Network reset · Factory reset
PUT /api/network/wifi Update WiFi SSID and password ▶
Used when the venue WiFi changes. Requires the User Secret in the Authorization header. Updates SSID/Password only; the User Secret cannot be changed via this API. The controller reconnects immediately, dropping the current session.
Request payload
{ "ssid": "NewVenueWiFi_5G", "password": "newp@ssword", "securityType": "WPA3" } // securityType: "WPA2"|"WPA3"|"WEP"|"OPEN"
Responses
// 200 OK — connecting to new network { "ok": true, "status": "reconnecting", "message": "Session will drop. Reconnect after join." } // 401 Wrong secret { "error": "invalid_secret" } // 400 Bad payload { "error": "invalid_payload", "message": "ssid is required" }
POST /api/network/reset Clear WiFi credentials — triggers BLE provisioning mode ▶
Clears stored WiFi credentials only. All device, group, scene, and effect data is preserved. Controller immediately enters BLE provisioning mode. Use this when moving the controller to a completely different network.
Request
POST /api/network/reset Authorization: Bearer <user-secret> // No body required
Responses
// 200 OK { "ok": true, "status": "ble_provisioning_mode", "message": "WiFi cleared. Use BLE to re-provision." }
POST /api/system/factory-reset Full factory reset — wipes everything ▶
⚠ Destructive — permanently deletes all devices, groups, scenes, effects, and WiFi credentials. Controller reboots into BLE provisioning mode. Cannot be undone.
Request
POST /api/system/factory-reset Authorization: Bearer <user-secret> // No body required
Responses
// 200 OK { "ok": true, "status": "factory_reset_complete", "message": "All data wiped. BLE provisioning mode active." }

Configuration
Fetched once per session · Models live in app not controller
ⓘ Fixture model definitions (channel count, channel labels, min/max values) are stored in the app, not fetched from the controller. The app assigns a modelId when adding a device and sends raw channel values for control. GET /api/config returns device list, groups, scenes, and effects only.
GET /api/config Full controller state — called once on every connect ▶
App caches in memory only — controller is the sole persistent store. No model definitions here; those are app-side.
Response 200
{ "controllerId": "DMX-CTRL-A4F2", "controllerName": "Stage Left", "devices": [ { "id": "d1", "name": "Spot 1", "uid": "06AE:00000001", "modelId": "m26", // app resolves this to channel map "dmxAddress": 1, "channelCount": 8, "sceneId": null, "effectId": null } ], "groups": [ { "id": "g1", "name": "Stage Left", "deviceIds": ["d1", "d2"], "sceneId": "sc1", "effectId": null } ], "scenes": [ { "id": "sc1", "name": "Warm Welcome", "targets": [ { "type": "device", "id": "d1", "values": { "1": 200, "2": 180 } }, { "type": "group", "id": "g1", "values": { "1": 150 } } ] } ], "effects": [ { "id": "ef1", "name": "Pulse", "loop": true, "steps": [ { "sceneId": "sc1", "duration": 2000, "fade": 500 } ] } ] }

Device (Fixture) Management
App assigns modelId · Controller stores address + channel count only
GET /api/devices List all configured fixtures ▶
// 200 OK { "devices": [ { "id": "d1", "name": "Spot 1", "uid": "06AE:00000001", "modelId": "m26", "dmxAddress": 1, "channelCount": 8, "sceneId": null, "effectId": null }, { "id": "d2", "name": "Wash 1", "uid": null, "modelId": "m12", "dmxAddress": 9, "channelCount": 2, "sceneId": null, "effectId": null } ] }
POST /api/devices Add a new fixture ▶
The app resolves the modelId locally. uid is the hardware RDM identifier (if applicable). Controller uses channelCount to check for DMX address overlap.
Request payload
{ "name": "Spot 2", "uid": "06AE:00000002", "modelId": "m26", "dmxAddress": 9, "channelCount": 8 }
Responses
// 201 Created { "id": "d3", "name": "Spot 2", "uid": "06AE:00000002", "modelId": "m26", "dmxAddress": 9, "channelCount": 8 } // 400 Address conflict { "error": "dmx_address_conflict", "conflictingDeviceId": "d2", "conflictRange": [9, 16] }

Request payload (all optional)
{ "name": "Spot 2 Renamed", "uid": "06AE:00000002", "modelId": "m27", "dmxAddress": 17, "channelCount": 8, "sceneId": "sc1", // optional: assign scene "effectId": null // only one of sceneId/effectId }
Responses
// 200 OK { "id": "d3", "name": "Spot 2 Renamed", "uid": "06AE:00000002", "modelId": "m27", "dmxAddress": 17, "channelCount": 8, "sceneId": "sc1", "effectId": null } // 404 { "error": "device_not_found" } // 400 Conflict { "error": "dmx_address_conflict" }

Effects Engine
Controller-global · No device/group in definition · App can disconnect
ⓘ Effects have no deviceIds or groupId — devices are implicit via the scenes in each step. Once started, the controller runs the effect loop independently.
GET /api/effects List all effects ▶
// 200 OK { "effects": [ { "id": "ef1", "name": "Pulse", "loop": true, "stepCount": 3, "status": "running" } ] }
POST /api/effects Create effect — sequence of scenes, no device list ▶
Request payload
{ "name": "Pulse", "loop": true, "steps": [ { "sceneId": "sc1", "duration": 2000, "fade": 500 }, { "sceneId": "sc2", "duration": 1500, "fade": 300 } ] } // duration ms · fade ms crossfade // No deviceIds or groupId — by design
Responses
// 201 Created { "id": "ef1", "name": "Pulse", "loop": true, "stepCount": 2 } // 400 Bad scene ID { "error": "invalid_scene_id", "badSceneId": "sc99" }
PUT /api/effects/{id} Update effect name, loop, or steps ▶
Request payload (all optional)
{ "name": "Fast Pulse", "loop": false, "steps": [ { "sceneId": "sc1", "duration": 500, "fade": 100 } ] }
Response
// 200 OK { "id": "ef1", "name": "Fast Pulse", "loop": false, "stepCount": 1 }

Real-time DMX Control — Raw mode only
App converts all UI values → raw 0–255 before sending
ⓘ All named parameter endpoints (dimmer, red, green, cct, strobe…) are removed. The app owns the channel map for each model and converts every UI interaction into raw DMX channel values before sending. The controller only receives channel numbers and 0–255 values.
POST /api/control/device/{id}/raw Send raw DMX channel values to one fixture ▶
Send only the channels that changed. Controller merges with current state. All values are 0–255. Channel numbering is relative to the fixture's DMX start address (ch 1 = start address, ch 2 = start+1, etc.).
Request payload
{ "channels": [ { "channel": 1, "value": 200 }, // Master dimmer { "channel": 2, "value": 180 }, // CCT { "channel": 3, "value": 0 }, // Color correction { "channel": 4, "value": 255 } // Red ] } // Array of channel objects // channel: 1–512, value: 0–255
Responses
// 200 OK { "ok": true, "appliedAt": "2026-05-10T10:30:00Z" } // 404 { "error": "device_not_found" } // 400 Value out of range { "error": "value_out_of_range", "channel": "4", "value": 300, "max": 255 }
POST /api/control/group/{id}/raw Broadcast raw channel values to all fixtures in group ▶
Controller applies each channel value only to fixtures that have that channel (i.e. whose channelCount ≥ the channel number). Mismatched channels are silently skipped per fixture — no error.
Request payload
{ "channels": [ { "channel": 1, "value": 150 }, { "channel": 2, "value": 0 }, { "channel": 3, "value": 255 } ] }
Responses
// 200 OK { "ok": true, "appliedToDevices": ["d1","d2","d3"] } // 404 { "error": "group_not_found" }
